# 0005. 品質確認はローカルで完結させ、GitHub Actionsは最小構成に限定する

日付: 2026-11-07
状態: 採用(2026-11-21改定: 関門のE2Eを差分の範囲に絞り、全件はissue-loopの終了時と公開前に回す)

## 背景
個人開発のprivateリポジトリで、開発はAIエージェントと対話しながらローカルで進める。E2EをCIで回すとローカルSupabaseの起動と本番ビルドで10分近くかかり、CI環境の遅さで不安定にもなった。
一方、ローカルではlint・型・単体テスト・E2E(13単元)が合計1分以内に通る。

## 決定
- **検査はローカルが正。** `pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm exec playwright test`(E2E)をローカルで回す。コンテンツやUIを変えたらE2Eを必ず回す(CLAUDE.md)。
- **push前のフック**でlint・型・単体テストを自動実行する(`.githooks/pre-push`。`git config core.hooksPath .githooks`で有効化。約30秒)。E2Eはフックに入れない(開発サーバーとSupabaseが要るため。エージェントと人が明示的に回す)。
- **GitHub Actionsは1ジョブだけ**(lint・型・単体テスト・ビルド、約45秒)。mainへのpushとpull requestで走る。目的は「別の環境でも依存関係と型が壊れていないこと」の確認で、ローカルの代替ではない。
- E2E・目視確認・性能計測はCIに入れない。

## 検討した代替
- CIを完全にやめる: 運用コストはゼロになるが、`pnpm install --frozen-lockfile`やビルドが別環境で通ることを確かめる手段が無くなる。45秒 × 月数十回なら無料枠(privateは2,000分/月)の数%で、維持する価値がある。
- CIでE2Eを回す: 上記の通り遅く不安定。必要になれば(複数人開発、公開前の回帰確認)手動起動のワークフローとして復活させる。

## 影響
- 新しい開発環境では`git config core.hooksPath .githooks`を1回実行する(README)。
- CIが落ちたら、まずローカルで同じコマンドを実行して再現する。

## 2026-11-21の改定: 関門のE2Eを差分の範囲に絞る
Issueを1件直すたびに回帰テストを`e2e/repro/`に足してきた結果、E2Eは11月7日の42本・22秒から803本になり、関門1回の中央値が3.4分、並列ループの負荷が重なると8.0分かかるようになった。関門は1件のIssueで2〜3回走る。「E2E込みで1分以内」という当初の前提は成り立たない。

- **関門(`scripts/check.sh`)のE2Eは、mainとの差分で決めた範囲だけ回す。** 規則は`scripts/e2e-scope.sh`が持つ。単元の本文(`content/topics/<テーマ>/<単元>.md`、`topic.yaml`)と`content/misconceptions.yaml`だけの変更は、基幹のspec(`e2e/*.spec.ts`。全単元を正解で通す`learning-loop`を含む)と、その単元を開くreproに絞る。追加・変更したspecは必ず回す。docsと単体テストだけの変更ではE2Eを回さない。`src/`、設定、概念・勘定科目・学習パスなど、範囲を決められない変更は全件を回す。
- **全件は2か所で回す。** issue-loopは、1件でも統合したら終了時に`scripts/full-check.sh`で統合後のmainを全件で確かめ、失敗すれば落ちたspecと統合したIssueの一覧を付けて`needs-triage`で起票する。`production`を進める前は`make check CHECK_E2E=full`を通す(ADR 0006)。
- **mainは、範囲の外のテストが壊れた状態を一時的に含みうる。** 壊れている時間は長くてループ1回分で、公開の前には必ず止まる。ADR 0012の「どのコミットも関門を通った状態」は、絞った関門についての保証になる。
- lint・型・単体テスト・ビルドは今までどおり毎回すべて回す。

直近200コミットに規則を当てると、全件が146件、絞れるものが51件(11〜149ファイル)、E2Eなしが3件だった。`src/`を触るIssueが7割を占めるので、関門の時間をさらに減らすには、採点や誤解判定のようにブラウザが要らないreproをVitestへ移す必要がある。
